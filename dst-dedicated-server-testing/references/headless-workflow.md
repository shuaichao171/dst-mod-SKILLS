# DST 通用无头测试流程

适用于《饥荒联机版》模组的自动引擎测试。使用原生专服执行实际模组代码，测试驱动负责布置环境、触发操作、采集证据和断言。用例、指标和驱动实现由当前任务确定，本流程不依赖某个模组或生物。

单分片离线场景已由 [../scripts/dst_headless_run.py](../scripts/dst_headless_run.py) 实现第 2、4、5、7 节的隔离、启动、判定与清理（用法见 SKILL.md「无头测试脚本」）；任务只需编写第 3 节的行为脚本。下文仍是多分片、自建控制器或审查脚本行为时的依据。

## 1. 定义测试目标与证据

先把待验证行为写成可观察的输入与结果，确定时间上限和通过条件，再编写驱动。语法检查、模拟单元测试、原生无头测试、真实客户端验证分别报告。

每次运行记录：

| 信息 | 内容 |
| --- | --- |
| 运行标识 | 唯一 run_id、开始时间、测试目的 |
| 软件基线 | 实际游戏 build、模组版本、加载端、依赖与加载顺序 |
| 源码基线 | 实际加载的模组、运行时依赖及测试驱动的文件清单与 SHA-256；Git 提交号不能代替未提交文件指纹 |
| 环境 | 世界设置、随机种子、配置、分片，以及影响结果的地形、装备、属性或时间调整 |
| 用例 | case_id、前置条件、操作、观测指标、断言、最大时长、必要的重复次数 |

- 在当前安装版本源码中核对目标 API、加载阶段和原生行为。游戏源码只读，修复落在模组中。
- 根据改动选择正常路径、边界、失败路径和相关生命周期用例；有随机性时记录种子，按风险选择重复或多个种子。
- 涉及“避免某种结果”或“性能提升”等结论时，安排能实际触发该结果的原版、关闭功能或修改前对照；对照未触发时不能据此宣称改进有效。
- 只验证部分阶段时，结论限于该阶段；启动成功、未报错或零次事件本身都不是功能通过证据。

## 2. 建立隔离环境

从工作流 `private/paths.md` 解析 `DST_GAME_HOME`、`DST_DATA_DIR` 等已配置路径，确认已安装的原生专服程序和版本。公开流程只使用占位名；测试目录由当前任务建立。缺少路径或可执行文件时明确记录环境缺口，不猜测安装位置，也不把模拟器结果记为无头通过。

建议每次运行独立保存以下内容；目录布局可按项目调整：

```text
RUN_DIR/
  plan/          用例定义、配置与源码指纹
  source/        被测代码和驱动快照，或可核验的构建产物
  storage/       独立持久化目录、Cluster 与世界存档
  ugc/           本次测试所需的独立模组缓存
  logs/          各进程原始日志，仅本地保留
  results/       结构化事件、逐例结果与脱敏报告
```

- 使用独立 Cluster、conf_dir、存储根目录和未占用端口，不指向用户的正常存档或生产服。
- 只加载目标模组、必要依赖和测试驱动。核实 `modinfo.lua` 的加载端与 `modoverrides.lua` 实际启用列表；纯客户端模组不会因启动专服就自动得到测试。
- 优先在隔离的模组加载位置放入快照。确需在游戏模组目录放测试包时，使用唯一目录名并记录所有权，不覆盖现有目录；配置、下载和缓存也保持隔离。
- 联机版的单进程离线场景可使用已安装版本支持的离线参数；需要在线连接的测试另按实际认证方式配置，凭据由本地工具读取，不写进用例或报告。

## 3. 编写测试驱动

测试驱动是单独的测试模组或控制台脚本，不进入正式发布包。优先调用真实模组入口和原生操作，让引擎推进实际逻辑；不要复制一份简化业务逻辑替代被测代码。

每个用例完成同一生命周期：

1. **准备**：创建必要的世界、实体、玩家或物品，等待原生初始化完成，安装本例观测器。
2. **断言前置条件**：确认实际地形、对象、阶段、加载端、组件和依赖符合用例要求；不成立则标为无效并记录原因。
3. **执行**：发出操作，让原生事件、组件、动作、AI 或状态机推进。需要跳转状态或加速时间时，记录影响范围，另保留能验证完整目标行为的用例。
4. **采集与判定**：按事件或限流采样收集结果，在完成条件或超时到达时输出逐例记录。
5. **恢复**：移除本例创建的实体、监听器和任务，恢复本例改动；污染无法可靠恢复时使用新世界或新进程。

驱动实现注意事项：

- 观测钩子应在相应实体创建和模块加载前注册；动态注册时验证确实收到事件，不能假设已缓存的 Prefab 会重新执行注册过程。
- 使用真实场景设施、地形与初始化链，并记录实际测量值；仅生成一个实体不代表相关世界系统已经就绪。
- 临时修改血量、光照、装备、时间倍率或 AI 都可能改变结论。记录实际生效值；不要禁用待验证的伤害、碰撞、存档或网络机制来让测试通过。
- 引擎适配层与业务代码分开。测试客户端逻辑时保持原有公开信息边界；在服务端借助完整组件数据运行的适配，不代表真实客户端也能得到这些信息。
- 多实体代理、共享状态或效果转发按真实持有者计数，避免对同一效果重复计数。持续变化需采集实际属性差值，不能只依赖某一种事件。
- 清理只作用于本例拥有的资源，不按半径或类别批量删除原生场景对象。需要覆盖睡眠、唤醒、移除或重载时，将其写成明确用例。

## 4. 启动与控制原生进程

启动前做当前改动所需的语法检查和快速回归；驱动自身也要检查。先跑一个最小用例，确认“启动 → 世界就绪 → 实际加载被测代码 → 驱动执行 → 结果输出 → 关服”的链路，再扩大测试矩阵。

以下是参数布局示意，并非可直接执行的命令；替换占位名，按当前程序实际支持情况核对参数，配置文件与命令行中的端口和分片保持一致：

```text
DST_SERVER_EXE
  -console -offline
  -persistent_storage_root RUN_STORAGE_ROOT
  -conf_dir RUN_CONF_NAME
  -cluster RUN_CLUSTER_NAME
  -shard Master
  -bind_ip 127.0.0.1
  -skip_update_server_mods
  -ugc_directory RUN_UGC_DIR
```

- `DST_SERVER_EXE` 是已核验的原生无渲染专服程序；工作目录按该程序要求设置。需要在线或跨机器测试时相应调整离线、监听与网络配置，不能照搬上面的本机示意。
- Windows 后台启动隐藏窗口。控制器保持进程句柄和必要的标准输入连接，分别保存标准输出、错误输出和游戏日志；不要依赖一次性管道持续发送后续命令。
- 记录各进程 PID、启动时间、程序和本次参数。通过明确的世界就绪标记及驱动握手后才开始计时；固定等待若干秒不足以证明加载完成。
- 检查空服暂停、世界自动暂停和实体睡眠是否符合用例要求，确认仿真时间及目标更新实际推进；进程仍存活不能证明测试正在执行。
- 控制台命令或控制文件通道使用唯一命令 ID 和完成确认，避免重复执行。定期输出进度；无进展、崩溃或超时要保留现场并结束该运行。
- 设置启动超时、单例超时和总时长上限。总预算包含生成世界、预热、全部用例、重启和关服余量；大矩阵可拆批，不能静默截掉尾部用例。
- 被测模组依赖专服读写集群目录内文件时，才追加 `-allow_persistentstorage_read_sandbox_escape` / `-allow_persistentstorage_write_sandbox_escape`（2026-10-27 热修 760178 新增的可选放行参数）；并为未加参数的情况补一个降级用例。

## 5. 记录指标并判定

指标随目标选择：组件或动作记录状态与实际效果，存档记录重载前后属性和引用，世界生成记录结构与合法性，战斗记录实际受伤、输出与控制状态，性能记录可比环境下的耗时或更新负载。避免用“调用了函数”代替“引擎产生了预期结果”。

逐例结果至少包含：run_id、case_id、代码与配置指纹、运行端、起止时间、前置断言、关键指标、最终状态、原因和证据位置。事件可用 JSONL，汇总可用 JSON 或表格；关联同一次运行、用例及实体，限制高频日志量。

| 状态 | 判定 |
| --- | --- |
| 通过 | 前置成立、执行完成，全部预设断言满足 |
| 失败 | 前置成立，实际行为不满足断言 |
| 无效 | 环境、驱动或观测不成立，无法判断被测行为 |
| 中断 | 崩溃、超时或停止导致未完成；已能证明的功能失败另行记录 |
| 未执行 | 用例未启动，注明原因 |

原生日志无错误只是检查项之一。无效、中断和未执行不能计入通过数。适配器测试、对照测试和目标功能用例分开统计；报告区分探索运行、最终代码回归及真实客户端测试。

## 6. 修复、复测与最终核验

失败先依据第一条相关错误和事件时间线区分模组问题、驱动问题与环境问题。模组问题在实际源码修复；驱动或环境问题修正后重跑，旧结果保留并说明为何无效。

- 每个候选版本保存新的源码指纹和运行标识，不覆盖历史失败证据。根据同一断言与可比条件判断改善，不能只选最好的一次结果。
- 修复后先复跑失败用例，再跑受影响的相关回归；已通过且不受影响的项目按需复用证据。
- 最终确认测试进程实际加载的快照与交付代码、依赖、配置一致。代码或影响行为的配置发生变化，相关旧结果不能直接作为最终通过证据；热重载范围不确定时重启验证。
- 保留仍未通过的场景和可复现步骤。不能用缩短时长、取消断言或削弱环境来替代修复。

## 7. 关服、清理与交付

1. 通过控制通道正常关服（例如当前版本支持的 `c_shutdown(false)`），等待退出并记录退出码。需要验证持久化时，先按用例显式完成保存和重载。
2. 正常关服超时时，核对进程句柄、启动时间和参数，再终止本次拥有的进程；记录强制终止及其对结果的影响。不按进程名批量停止游戏或用户原有服务器。
3. 确认本次各分片、控制器和辅助进程均已退出；清理本次测试模组和临时配置，保留复现所需的快照、存档及结果。移动或删除前核验解析后的绝对路径仍在本次拥有的目录内。
4. 汇总测试范围、版本与指纹、有效用例数、通过/失败/无效/中断/未执行数、关键指标、剩余问题和清理结果。分享前脱敏路径、身份及认证信息；原始日志默认本地保存。

本流程验证引擎逻辑，不能证明贴图实际显示、UI 操作、音画表现、真实客户端预测、远端网络同步或真实游玩性能。报告按任务明确这些边界，需要时追加相应测试。
